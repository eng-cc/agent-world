# 产品文档模板与迁移卡

- 配套规范：[`product-documentation-standard.design.md`](product-documentation-standard.design.md)
- 模板性质：可复用写作结构，不是新的任务、数据库 schema 或自动门禁
- 使用边界：保留现有根身份、SC/验收 ID、专业 PRD-ID 和已验证事实；占位符必须替换为真实内容并标明性质

## 1. 根 PRD 补充模板

四个根 PRD 继续使用仓库现有身份和标题顺序。按需在现有章节加入以下子节，不用空模板覆盖正文：

```markdown
## 文档身份
- 产品模块：〈四个既有模块之一〉
- 产品模块 slug：`〈既有 slug〉`
- 产品层唯一 PRD：`〈现有 prd.md〉`
- 产品模块总入口：`doc/product/README.md`
- Product PRD-ID：`〈现有稳定 ID〉`
- 生命周期：`active`
- Owner role：`〈真实 owner〉`
- Last reviewed：`〈真实复核日期〉`
- 后继文档：`〈无，或填写真实后继文档〉`
- 下层专业域：〈真实链接〉

### 活跃产品专题
〈只列实际 active 专题；候选稿不进入 active 清单。〉

## 1. 产品承诺
### 1.1 玩家与问题
### 1.2 体验与能力目标
### 1.3 核心体验总览

## 2. 范围
### 2.1 适用入口与阶段

### 2.3 模块组合

## 3. 权威与冲突处理
## 4. 路线图
## 5. Done：成功标准与验收
### 5.1 验收追踪
## 6. Non-Goals
```

根成功标准保留原 ID、顺序和六列追踪；复杂义务用稳定下钻链接承接，不因套模板删减原语义。

## 3. 产品 design 模板

```markdown
# 〈专题〉产品设计

## 文档身份
- 配对产品 PRD：〈同名 PRD〉
- 上位产品 PRD：[`prd.md`](prd.md)
- 生命周期：`〈实际状态〉`
- Owner role：`〈真实 owner〉`
- 专业域权威：〈规则、数值与实现 authority〉

## 1. 设计命题
目标体验：〈从什么状态到什么状态〉。
核心决策：〈在什么信息与约束下选择〉。
假设与反证信号：〈未证明部分〉。

## 2. 代表性片段
〈目标 → 选择 → 后果 → 下一决策；示例值明确不是正式参数。〉
## 3. 机制与体验关系
| 体验目标 | 玩家决策 | 权威约束 | 预期互动结果 | 失败信号 |
| --- | --- | --- | --- | --- |
## 4. 循环与成长
## 5. 行为与后果
## 6. 资源与平衡影响（适用时）
## 7. 失败、阻塞与恢复
## 8. 表现与可访问性（适用时）
## 9. 取舍与验证
```

交互主题必须额外说明对象/身份、可见信息、授权、主动作、提交成本、结果、状态优先级、重连/重复/外部变化和真实恢复路径；不把控件位置或历史布局当成承诺。

## 4. 需求、验收与未决卡

### 4.1 叶子需求卡

```text
标识：文档路径#req-xxx
适用条件：入口、阶段与前置
规范要求：主体 + MUST/MUST NOT + 一个可判断结果
设计理由：玩家价值
上位引用：既有 SC 或稳定章节
专业依据：真实 authority 与 PRD-ID
验收引用：AC-xxx
```

### 4.2 验收场景卡

```text
标识：文档路径#ac-xxx
覆盖要求：一个或多个 REQ（逐项判定）
给定：有界前置状态
当：一次明确触发
则：可观察结果
证据范围：入口、版本/范围、窗口、环境
验证入口：专业测试/manual/正式证据
非证明项：该场景不能推出什么
```

### 4.3 未决问题卡

```text
尚未决定：准确问题
影响：REQ/AC、授权、成本、状态或验收
决策负责角色：真实 role
需要的信息：调研/分析/实验
解决触发条件：进入哪一范围前必须解决
任务引用：正式 GitHub task
临时范围：解决前明确排除的保证
```

## 5. 代表性迁移模式

### 5.1 Prompt 交互

Prompt 主题必须保留：目标 Agent 与控制资格、对话/配置区分、预设与草稿、默认/override、accepted/applied、响应式与输入、控制权丢失优先于值变化、stale 恢复、提交时重新校验和竞态至多一个真实 authority 结果。建议用 `REQ-PROMPT-*` / `AC-PROMPT-*`，并逐项回链配对 design 的状态模型和 `doc/world-simulator` authority。

### 5.2 首局与持续游玩

完整主题至少描述：玩家主目标与动作、工厂就绪、配方比较、原料准备、物流抵达、多输入齐套、排程、生产 receipt、交付 receipt、原材料子循环、Starter Industrial Feasibility Gate、失败恢复、首局/持续能力区分和 Viewer/pure API 入口证据。不要把一条完整 walkthrough 拆成静态任务清单，也不要删掉原文中对顺序、适用性、资源守恒和重复提交的限定。

### 5.3 复杂根 SC

根 SC 保持原组合目标和追踪行。叶子分解可按提交前比较、生产/交付、盈余处置、缺口/补产、状态变化、重复执行、多入口一致性组织，但每条都要回到原条款和 `gameplay` 专业 authority；产品治理 slice 不代替玩法专业迁移。

## 6. 审查卡

- [ ] 四模块入口、专题可达、根回链和专业 authority 仍有效。
- [ ] 有具体情境、完整正常路径、真实选择、代价、结果和下一步。
- [ ] 叶子 REQ 单独可判定，AC 场景与专业入口可定位。
- [ ] 目标态、事实、假设、当前能力和公开承诺没有混写。
- [ ] 失败、授权、重复、回流和恢复覆盖本主题真实风险。
- [ ] 未复制任务台账、实现字段、测试步骤或历史 verdict。
- [ ] 没有以结构 checker 通过代替产品/玩法/体验评审。
